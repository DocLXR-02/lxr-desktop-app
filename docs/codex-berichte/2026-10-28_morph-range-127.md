## Compatibility decision: no stored legacy amount to migrate

**CODE:** Supported kits, temporary kits, patterns, global settings and projects do not store the Morph amount. It is a runtime control in the gap between sound and global parameter blocks. A legacy kit may contain sound bytes above 127, including eligible eight-bit sound parameters; these are not Morph amount bytes and are not rescaled or clamped. Existing normalization of historical modulation target indices is unchanged.

A previously saved Morph Kit already contains baked sound values. Loading it retains those bytes; it is not reinterpreted as a saved knob position. No file migration or rewrite is performed. Ordinary kit saves, all pattern layouts, globals and project layout remain unchanged. Successful saves at equivalent underlying interpolation fractions remain byte-identical to the original oracle.

Numeric knob recipes necessarily change: the previous raw range of 0–255 is compressed into 0–127. An old halfway amount around 127 maps approximately to new 63/64, while old full travel maps to new 127. There is no recorded Morph automation target in the supported table to rescale. Custom external tools that directly manipulate runtime RAM or call internal APIs with old units are not a supported file format; requests above 127 now saturate to the destination. Supporting such a private interface would require an explicit protocol and is **OPEN**, not assumed legacy compatibility.

No arbitrary bytes inside old files are treated as Morph values. This avoids damaging valid 8-bit sound parameters or inventing a version flag.

## Minimal implementation and numerical reasoning

Only the following production lines changed:

```c
/*PAR_MORPH*/             DTYPE_0B127,
```

```c
// Morph control is 0..127; retain the existing 8-bit fractional precision
// and intermediate rounding. The destination endpoint is exact.
static uint8_t interpolate(uint8_t a, uint8_t b, uint8_t x)
{
    if(x >= 127) return b; // Saturate invalid internal amounts as well.
    const uint16_t fraction = ((uint16_t)x * 256u + 63u) / 127u;
    uint16_t fixedPointValue = (uint16_t)((a*256) + (b-a)*fraction);
    uint8_t result = (uint8_t)(fixedPointValue/256);
    return (uint8_t)((fixedPointValue&0xff) < 0x7f ? result : result+1);
}
```

At `preset_morph()` entry:

```c
// Runtime-only control: no kit, pattern or project field is rescaled.
activeParameters[PAR_MORPH] = morph > 127 ? 127 : morph;
```

For x < 127 the internal fraction is the nearest integer to `256*x/127`. The existing 1/256 fixed-point accumulator and intermediate rounding rule are retained. At x=0 the result is exactly a. At x>=127 it is exactly b. The accumulator stays in 0–65280; integer promotions on the actual ARM/native compilers keep the signed difference and product within int range. The new denominator is intentional: merely limiting the old fraction to 127 would leave the transition approximately half complete.

The two central control steps straddle the mathematical midpoint. For source 0 and destination 127, x=63 returns 63 and x=64 returns 64. All 65,536 source/destination byte pairs at all 128 legal amounts were tested for monotonicity, bounds, exact endpoints and at most one output LSB deviation from ideal rational interpolation. The existing rounding threshold is 0x7f; its old “bankers rounding” comment was inaccurate and was replaced, without changing the intermediate rule.

The old raw-255 implementation used `255/256`, which could miss b for large differences. An explicit new endpoint ensures the full destination rather than reproducing that approximation. This is the intended endpoint correction, not a filter curve change.

Pre-existing exceptions remain: live Morph preserves source audio routing and does not execute transport slots; baked Morph Kits preserve source modulation target/target-voice choices. “Full destination” applies to the parameters already designated morphable by these paths. No routing behavior was broadened.

## Remaining risks and next action

**CODE/BUILD:** Full control travel is now represented by 128 positions; retaining eight-bit fractional math cannot create more than those 128 distinct user steps. There may be perceptual differences in the spacing of sound changes versus the former 256-position UI. The mapping, intermediate rounding and target endpoint are explicit and exhaustively checked, but listening is still required.

**CODE:** Morph routing and baked-kit target exceptions remain as before. Loading kits does not restore a saved amount because no amount exists in those files. Previously baked sound data remains intact. There is no migration or background rewrite.

**OPEN:** Actual absence of clicks during normal and repeated endpoint movement must be checked on hardware, including high Filter Drive and differing source/destination kits. No claim of measured audio stability, CPU headroom, storage durability or hardware readiness is implied by these builds. User-reported testing of the baseline does not validate this changed image.
